# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

SisHospedar is a hotel management system (ASP.NET Core MVC, .NET 10, EF Core 10, SQL Server, Razor + Bootstrap 5). It's a modernization of a .NET Framework/Web Forms/ADO.NET TCC project — the rewrite's explicit goals were removing the hardcoded connection string, hashing employee/guest passwords, and replacing manual ADO.NET DAOs with EF Core. Keep those goals in mind: don't reintroduce plaintext secrets/passwords or hand-rolled SQL.

## Project scope and status

Considered feature-complete for what it set out to do: modernize the 2013 TCC with a current architecture (EF Core, real ASP.NET Core Identity, automated tests, cloud deploy with CI/CD) and fix the original's security problems (plaintext passwords, hardcoded connection string, hand-rolled SQL). Two things are deliberately **out of scope, not deferred** — don't propose or implement either unless the user explicitly reopens the question:

- **Payment processing.** This is a learning project with no commercialization intent. A real gateway integration (Stripe/Mercado Pago/PagSeguro) would add compliance and security surface (card data, chargebacks) disproportionate to what the project demonstrates, without teaching anything the rest of the stack hasn't already covered.
- **A REST API.** The app already covers its own needs through MVC; there's no real external consumer (a mobile app, a third-party integration) that would justify one today.

New feature work in this repo should generally be maintenance, polish, or something the user explicitly asks for — not organic expansion toward either of the above.

### Deploy

Runs in production as a container: `Dockerfile` (multi-stage: SDK to build/publish, `aspnet:10.0` runtime for the final image, listens on `:8080` via `ASPNETCORE_URLS`) → pushed to Docker Hub (`wesleysales/sishospedar`) → running on Azure Container Apps (`env-sishospedar`/`sishospedar`, resource group `rg-sishospedar`), backed by Azure SQL Database (`sql-sishospedar-wsales-br`, Basic tier).

Redeploy is automated: `.github/workflows/ci.yml`'s `deploy` job runs on every push to `main` that passes `build-and-test`, and tags the image with the commit's short SHA (never a bare `:latest` — Container Apps only creates a new revision when the image *string* changes, and reusing `:latest` once let a bug ship without the site actually updating). It authenticates to Azure via a Service Principal scoped to just `rg-sishospedar` (`AZURE_CREDENTIALS` GitHub secret) and to Docker Hub via `DOCKERHUB_USERNAME`/`DOCKERHUB_TOKEN`. New migrations still need `dotnet ef database update` run against the production connection string manually (see README's Deploy section) — the pipeline deliberately never applies migrations automatically, to keep anything schema-destructive under direct supervision.

Azure App Service (the original plan) hit a hard blocker: the subscription had zero quota for the free F1 tier in every region tried (~9), and quota-increase support tickets require a paid support plan this subscription doesn't have — self-service quota requests only work through the Portal UI, not the API/CLI. Container Apps uses a separate (consumption-based) quota pool and wasn't affected, which is the entire reason it's the current host instead.

### Tests (`SisHospedar.Tests/`)

xUnit integration tests using `WebApplicationFactory<Program>` — boots the real app in-memory and swaps the SQL Server `AppDbContext` registration for **in-memory SQLite** (`CustomWebApplicationFactory`), so `dotnet test` needs no real database. Swapping the provider means removing **two** DI registrations, not one: `DbContextOptions<AppDbContext>` *and* `IDbContextOptionsConfiguration<AppDbContext>` (`Microsoft.EntityFrameworkCore.Infrastructure`). Since EF Core 9, `AddDbContext` registers the latter to hold the provider callback, so removing only the former leaves `Program.cs`'s `UseSqlServer` behind and every test dies at startup with "Only a single database provider can be registered in a service provider." SQLite (not EF Core's "InMemory" provider) is required because `ConsumoController.Create`'s atomic stock decrement uses `ExecuteUpdateAsync`, which the InMemory provider cannot translate — SQLite is a real relational engine and supports it. `Program.cs`'s own seed data runs against that database on host startup, so tests reuse the known seeded logins (`wesley.sales`/`luan.santos`/`matias.sampaio`/`camila.rocha`/`diego.fernandes` — one per `CargoFuncionario`, login always `firstname.lastname`, password `Senha123`) instead of re-seeding; tests needing specific scenario data (a room in a given `StatusApartamento`, a `Consumo` against a controlled stock level, etc.) insert it directly via `CustomWebApplicationFactory.UsandoContextoAsync`.

`SisHospedar.Tests` lives as a subfolder of the main project's directory (not a sibling) — `Microsoft.NET.Sdk.Web`'s default `**/*.cs` glob would otherwise try to compile it into the web project too, so `SisHospedar.csproj` explicitly excludes it (`<Compile Remove="SisHospedar.Tests/**/*.cs" />`). `Program.cs` ends with `public partial class Program { }` so the test project can reference it — top-level-statement `Program` is `internal` by default, and that's a hard C# accessibility-domain rule that plain `InternalsVisibleTo` does not work around for generic base classes like `WebApplicationFactory<Program>`.

Coverage: `AutorizacaoFuncionarioTests` (anonymous access redirects, wrong `Cargo` gets 403, guest vs. employee identity separation) and business-logic tests — `ConsumoTests` (stock deduction, insufficient-stock rejection, rejecting consumption on a finalized stay), `HospedagemStatusTests` (check-in occupies the room, check-out frees it), `ReservaConfirmarTests` (confirming a booking creates the `Hospedagem` and occupies the room, or fails gracefully if the room is no longer free), `IdentityTests` (account lockout after repeated invalid attempts, and the full password-reset round trip through `/Conta/EsqueciSenha` → `/Conta/RedefinirSenha`), `RegistroHospedeTests` (real CPF check-digit validation rejecting both a wrong check digit and an all-same-digit sequence, and the Login/Email required-field errors that only apply to self-registration). Shared HTTP/login/antiforgery helpers live in `TestesIntegracaoBase`. Writing `HospedagemStatusTests.FinalizarConfirmado_LiberaApartamento` caught a real, pre-existing bug: `Views/Hospedagem/Finalizar.cshtml`'s form posted a `HospedagemId` field while the action expected a route parameter named `id` (no `asp-route-id`), so the "Confirmar Finalização" button always 404'd in the real app — fixed by adding `asp-route-id="@Model.HospedagemId"` to the form.

### CI (`.github/workflows/ci.yml`)

Runs on every push/PR to `main`: restore, build (Release), `dotnet test`, then `dotnet ef migrations has-pending-model-changes` — the last step is what would have caught the `InitialCreate`-vs-model drift found earlier in this project (missing `Hospede.Login`/`Reservas`/etc.) before it ever reached a clone. None of this needs a real SQL Server: the workflow sets `ConnectionStrings__DefaultConnection` to a dummy value purely to satisfy `Program.cs`'s startup guard clause — tests run against in-memory SQLite, and the pending-migrations check only compares the in-code model against the last migration's snapshot, no live connection required.

### Observability

There is no APM and no telemetry package (Application Insights/OpenTelemetry/Serilog would all add cost or dependencies the project doesn't need). Observability is the container's stdout: Container Apps ships it to a Log Analytics workspace (30-day retention), queryable with KQL via `az monitor log-analytics query`. The workspace has a **0.2 GB/day ingestion cap** — roughly 650× normal usage — set deliberately as a guard against a runaway log loop generating a bill on a project with no budget.

Two logging rules this project settled on, both learned from reading real production logs:

- **`Microsoft.EntityFrameworkCore.Database.Command` is pinned to `Warning`** in `appsettings.json`. At the inherited `Default: Information` it logged every SQL statement, and 82 of 91 log lines in a 24-hour window were SQL — the real signal was unreadable. (`EnableSensitiveDataLogging` is off, so parameter *values* never reached the logs even then; only the statement shape did.)
- **Business events are logged in `Services/`, never in controllers, and carry ids only — never `Nome`, `Cpf`, `Email` or any PII**, since logs are long-retained and broadly readable. `AutenticacaoService` logs *only* account lockout, not individual failed attempts: someone typing their password into the username field would otherwise write their own password into a retained log, and lockout is the rare, actionable event worth attributing to an account.

`/health` is a liveness endpoint (`AddHealthChecks()` with no registered checks) — deliberately **not** a database check, because the Azure SQL is Basic tier (5 DTU) and a periodic probe querying it would consume capacity the app itself needs.

**Data Protection keys live in the database** (`AppDbContext.DataProtectionKeys` via `PersistKeysToDbContext<AppDbContext>()`, migration `PersistenciaChavesDataProtection`). The default is to write them to disk inside the container, which Container Apps discards on every deploy — production logs showed one new key ring per container start and a daily `AntiforgeryValidationException` ("key not found in the key ring"), meaning every deploy silently signed out all users and broke any form that was already open. The existing SQL database was chosen over Blob Storage or Key Vault specifically because it adds no paid resource. The remaining `XmlKeyManager` warning ("No XML encryptor configured") is accepted: encrypting the key ring at rest would require Key Vault, and Azure SQL already encrypts at rest via TDE.

### LGPD

The app holds real categories of personal data (`Hospede.Nome`/`Cpf`/`Telefone`/`DataNascimento`/`Email`), so the data-subject rights that require touching the database live in `IPrivacidadeService`/`PrivacidadeService`: access (Art. 18, II) via `/Cliente/MeusDados`, portability (Art. 18, V) via `/Cliente/ExportarDados` (JSON, because the law asks for an interoperable format), and erasure (Art. 18, VI) via `/Cliente/ExcluirConta`. The public notice is `/Privacidade` (`PrivacidadeController`, deliberately outside any authorization filter so someone can read it before creating an account), linked from the footer on every page.

Three decisions here are deliberate and shouldn't be "simplified" away:

- **Erasure is not always deletion.** A guest with no stay and no booking is genuinely deleted. A guest *with* history is **anonymized** instead — Art. 16 allows retaining what a legal obligation requires (the stay record and its financial entries) and Art. 12 treats anonymized data as no longer personal. `PrivacidadeTests` pins both branches precisely so a future refactor can't collapse them and silently erase fiscal history. Deletion is also refused outright while a stay is open or a booking is pending, since the hotel still needs to know who occupies the room.
- **`Cpf` gets a marker, not null, on anonymization** (`ANON{id:D8}`): the column is `[Required]`, `StringLength(14)`, and carries an **unfiltered** unique index, so it needs a non-null unique value. (`Login`/`Email` *can* be nulled — their unique indexes are filtered.) The marker fails `[CpfValido]`, which is fine: that validator only runs on form binding, never against a stored row.
### Consent management and first-party analytics

The site measures its own audience — no Google Analytics, no third-party script, no international data transfer. `IAnalyticsService`/`AnalyticsService` plus `RegistroVisitaMiddleware`, with the consent UI in `PrivacidadeController` (`Preferencias`, `Consentimento`) and the banner in `_Layout`.

The split that makes the consent *real* rather than decorative:

- **Aggregate hit counting runs for everyone, with or without consent.** `VisitaPagina` holds one row per path per day — a counter, not a visit log. No identifier means no personal data means no consent to ask for.
- **Only the new-vs-returning distinction is gated**, because that requires writing `SisHospedar.Visitante` (a random id) to the browser. Accepting and refusing therefore produce *different, observable* outcomes — which is exactly what the Airbnb-style "accept all / necessary only" pair would not have done here, since at the time there was nothing optional to gate.

Decisions worth preserving:

- **The measurement cookie is never written before the answer.** That prior gate is the thing most Brazilian sites get wrong (write first, ask later). `ConsentimentoTests` pins it.
- **Refusal is stored too** (`SisHospedar.Consentimento` = `recusado`), otherwise the banner would reappear on every page — nagging until the person gives in is the dark pattern the ANPD objects to. Refusal also *deletes* the existing identifier rather than merely not renewing it.
- **Accept and Refuse are sibling buttons of equal prominence** in the banner, and `/Privacidade/Preferencias` exists as a permanent place to revoke, because Art. 8º §5º makes consent revocable at any time and a banner that vanishes after one click doesn't satisfy that.
- **The banner is server-rendered and uses plain POST forms — no JavaScript at all.** It's emitted only while no decision cookie exists, so it disappears on its own. (An earlier JS + localStorage version was deleted once the decision moved to a cookie; the server already knows, so the script was dead code.)
- **`ConsentimentoCookie.IdentificadorAnonimo` is deliberately NOT sent to the browser.** Returning it would make each consent record re-linkable to a specific browser — the table that exists to prove privacy compliance would itself become a tracking identifier. It also stores no IP, no user-agent and no `HospedeId`, and the tests assert those properties don't exist.
- **`returnUrl` on the consent POST is validated with `Url.IsLocalUrl`** — it comes from a form, so an unvalidated redirect would be an open redirect.

Two implementation notes:

- **Visits are buffered in memory (`BufferVisitas`, singleton) and flushed by `FlushVisitasService` every 60s**, never written per request. The Azure SQL is Basic tier (5 DTU) and the home page was optimized precisely to stop hitting it on every visit; a synchronous write per pageview would have undone that. `Drenar()` swaps the whole dictionary atomically so no increment is lost mid-drain, and the `BackgroundService` opens its own scope per cycle — resolving the scoped `AppDbContext` in its constructor would keep one context alive for the process lifetime. Accepted trade-off: counts from the current interval are lost if the container dies.
- **The unique index on `(Caminho, Data)` is what allows the atomic increment** (same `ExecuteUpdateAsync` pattern as the stock decrement): concurrent flushes can't create duplicate day rows, and the insert path catches `DbUpdateException` and retries the update. `RegistroVisitaMiddleware` also normalizes numeric path segments to `{id}`, so the table grows with pages, not with data.

- **There is no consent checkbox on registration, on purpose.** The legal basis for the guest data is contract execution (Art. 7º, V) plus legal obligation (Art. 7º, II), *not* consent; asking for consent you cannot honor the withdrawal of would misrepresent a choice the user doesn't have. (Cookies are a separate matter — see the consent section above, which covers the one genuinely optional cookie.)

One implementation trap worth keeping, because it fails *silently*: **`wwwroot/img/sishospedar-marca.svg` must not contain `--` inside its XML comment.** A double hyphen is illegal in XML comments, and naming the CSS custom properties (`--stone`, `--surface-alt`) in there made the whole file unparseable — the browser rendered a broken image with no console error on the host page. The comment now names them without the leading hyphens.

`Views/Privacidade/Index.cshtml` opens with a prominent notice that this is a demo system and users should not enter a real CPF. That callout is the project's main practical protection: a publicly reachable demo holding real CPFs would be genuine personal data with genuine controller obligations attached.

## Architecture

Standard ASP.NET Core MVC, one `DbContext` (`Data/AppDbContext.cs`), no repository layer. Read-only queries (`Index`/`Details` listings, `SelectList` sources) stay inline in controllers via `_context` directly — no repository wrapping needed for those. Non-trivial business logic with side effects (stock deduction, `Apartamento.Status` transitions, reservation confirmation) instead lives in `Services/`: `IHospedagemService` (check-in/check-out), `IConsumoService` (consumption + atomic stock decrement), `IReservaService` (guest booking creation + reception confirm/cancel). Each service method returns `(bool Sucesso, string? Erro)` (or a small enum/nullable-string variant where the caller needs different branching, like `NotFound()` vs. a `ModelState` error) — controllers translate that into `ModelState.AddModelError`/`TempData`/redirects, they don't re-derive the business rule. When adding new business logic with side effects, add it to the relevant service (or a new one) rather than back into the controller — that's what made this logic unit-testable via `SisHospedar.Tests` without going through the full HTTP pipeline for every case, and it's also what keeps the original 22 tests (now 24, see below) as a regression net: they were written before the service extraction and still pass unchanged against it.

### Two separate user identities, both cookie-authenticated, both backed by real ASP.NET Core Identity

Authentication is plain ASP.NET Core cookie authentication (`Microsoft.AspNetCore.Authentication.Cookies`) with **two independent schemes** — not `Session`. `Funcionario` and `Hospede` stay the plain EF Core entities they've always been (no `IdentityUser<T>` inheritance, no renamed `FuncionarioId`/`HospedeId`/`Login`); only the *auth transport* is a signed cookie carrying claims. Scheme names live in `Authentication/Esquemas.cs` (`Esquemas.Funcionario`, `Esquemas.Hospede`); both are registered in `Program.cs` via `AddAuthentication().AddCookie(...)` twice — **neither is the default scheme**, so every `[Authorize]` in this codebase names its scheme explicitly (directly, or via the `Requer*` attributes below). This cookie layer is completely separate from — and unaffected by — the Identity layer described next: `SignInManager`/`UserManager` never write a cookie of their own here, only password verification/lockout/reset run through them.

Password verification, hashing, failed-attempt lockout, and password-reset tokens run through real ASP.NET Core Identity (`UserManager<Funcionario>`, `UserManager<Hospede>`, `SignInManager<Funcionario>`, `SignInManager<Hospede>`, registered in `Program.cs` via `AddIdentityCore<T>()` — not `AddIdentity`/`AddDefaultIdentity`, which would try to register their own cookie scheme). They're backed by `EntityUserStore<TEntity>` (`Authentication/EntityUserStore.cs`), a custom store reading/writing straight into `Funcionario`/`Hospede`'s existing columns via `IContaAutenticavel` (`Models/IContaAutenticavel.cs`) — chosen specifically to avoid the two things that made a naive Identity migration look expensive: inheriting `IdentityUser<T>` (which would force renaming the primary key and `Login`) and the EF Core `IdentityDbContext`-style `UserStore` (which needs per-identity duplicate support tables — `UserClaims`/`UserRoles`/`UserTokens` — since two different `IdentityUser`-derived types can't share one set of those tables). `Funcionario`/`Hospede` gained four columns for this: `SecurityStamp`, `AccessFailedCount`, `LockoutEnd`, `LockoutEnabled` (migration `AdicionaCamposIdentity`). **Any account created outside `UserManager.CreateAsync` (i.e., `Program.cs`'s seed data) must set `SecurityStamp` itself** — Identity throws `InvalidOperationException` ("User security stamp cannot be null") the moment it tries to validate such a user (e.g., while counting a failed login attempt), since `CreateAsync` normally sets it automatically and nothing else does.

- **Funcionário (employee)** — `AutenticacaoService.AutenticarAsync` (see below) calls `SignInManager<Funcionario>.CheckPasswordSignInAsync(funcionario, senha, lockoutOnFailure: true)`, then on success manually builds a `ClaimsPrincipal` (`ClaimTypes.NameIdentifier` = `FuncionarioId`, `ClaimTypes.Name` = `Nome`, `ClaimTypes.Role` = `Cargo`) and calls `HttpContext.SignInAsync(Esquemas.Funcionario, principal)` itself — `SignInManager`'s own cookie-writing methods (`PasswordSignInAsync`, etc.) are never called, only the password/lockout check. `HomeController.Logout` calls `SignOutAsync(Esquemas.Funcionario)`. Employee-only controllers/actions are gated by two attributes in `Filters/`, both thin `AuthorizeAttribute` subclasses: `[RequerFuncionario]` (`[Authorize(AuthenticationSchemes = Esquemas.Funcionario)]` — valid cookie required, no role check) and `[RequerCargo(params CargoFuncionario[])]` (also constrains `Roles` to the given cargos — used on `FuncionarioController` for `Administrador`/`Gerente`-only staff management). No cookie → the cookie handler's `LoginPath` (`/Home/Login`) redirects automatically (with a `?ReturnUrl=`, unlike the old session redirect). Right cookie, wrong role → the handler's `OnRedirectToAccessDenied` event is overridden in `Program.cs` to return a bare 403 instead of the default redirect-to-`AccessDeniedPath` (which doesn't exist in this app).
- **Hóspede (guest/customer)** — same shape, `Esquemas.Hospede`: `AutenticacaoService` calls `SignInManager<Hospede>.CheckPasswordSignInAsync`, and on success `ClienteController`'s private `AssinarCookieAsync` helper builds a principal (`NameIdentifier`/`Name` only, no role — guests have no `Cargo`) and calls `SignInAsync`; `Logout` calls `SignOutAsync(Esquemas.Hospede)`. Guest-facing self-service actions (`MinhaConta`, `Prorrogar`, `SolicitarEncerramento`) and the guest half of `ReservaController.Create` (GET+POST) are gated by `[RequerHospede]` (`Filters/RequerHospedeAttribute.cs`), reading the guest's id back out via `User.FindFirstValue(ClaimTypes.NameIdentifier)` instead of `Session.GetInt32`.
- Apply the attribute at the class level when every action needs it (`HospedagemController`, `ApartamentoController`, etc.); apply it per-action when a controller mixes identities, like `ReservaController` (`[RequerHospede]` on guest `Create`; `[RequerFuncionario]` on employee `Index`/`Confirmar`/`Cancelar`).
- **Views that aren't behind either attribute** (the public `Home/Index`, and `Shared/_Layout.cshtml`'s navbar, rendered on every page) can't rely on `User`/`HttpContext.User` being populated — with no default scheme, nothing authenticates it automatically outside an `[Authorize]`-guarded request. They instead call `await Context.AuthenticateAsync(Esquemas.X)` explicitly and check `.Succeeded` (ASP.NET Core caches the result per scheme per request, so calling it from both the layout and a child view isn't wasted work). Views reached *through* a `Requer*`-guarded action (`Painel/Index.cshtml`) can just read `User.FindFirstValue(...)` directly, since authorization already populated `User` from the right scheme for that request.

When adding a new employee-only controller/action, use `[RequerFuncionario]`/`[RequerCargo]` (or `[RequerHospede]` on the guest side) rather than reintroducing an inline claims/cookie check — the whole point of the attributes is that forgetting to protect a new action is no longer possible by omission the way a copy-pasted check could be forgotten (this happened for real: 5 controllers once shipped with zero session checks before these attributes existed).

### Domain flow: Reserva → Hospedagem → Consumo

- `Reserva` = a guest's online booking request (`StatusReserva`: Pendente/Confirmada/Cancelada). Created by the guest via `ReservaController.Create` (guest-side).
- Reception confirms via `ReservaController.Confirmar` (employee-side), which is the check-in point: it creates the actual `Hospedagem` record and flips the `Apartamento.Status` to `Ocupado`. `Hospedagem` can also be created directly by reception without a prior `Reserva` (`HospedagemController.Create`).
- `Consumo` (product consumption during a stay) is added via `ConsumoController.Create`, which decrements `Produto.Estoque` and is tied to a `Hospedagem`.
- Ending a stay is `HospedagemController.Finalizar`/`FinalizarConfirmado` (employee side — sets `Finalizada = true`, `DataSaida`, and frees the apartment back to `Disponivel`) or the guest can flag `SolicitouEncerramento = true` via `ClienteController.SolicitarEncerramento`, which reception then acts on.
- `Apartamento.Status` (`Disponivel`/`Ocupado`/`Manutencao`) is the single source of truth for booking eligibility — every action that creates/confirms/ends a stay must keep it in sync; there's no separate availability-calculation logic.

### EF Core model notes (`Data/AppDbContext.cs`)

- Unique indexes: `Hospede.Cpf`, `Hospede.Login`, `Hospede.Email`, `Funcionario.Login`, `Funcionario.Email`, `Apartamento.Numero`. Both `Email` indexes are filtered (`WHERE Email IS NOT NULL`) since the column is optional — any number of accounts can have no email, but no two can share one within the same table.
- FKs to `Hospede`/`Apartamento` from `Reserva`/`Hospedagem` use `DeleteBehavior.Restrict` (no cascade); `Consumo → Hospedagem` cascades, `Consumo → Produto` restricts.
- Money fields (`Apartamento.ValorDiaria`, `Produto.Preco`, `Consumo.ValorUnitario`) are `decimal(10,2)`.
- `Hospedagem.TotalConsumo` and `Consumo.ValorTotal` are computed `[NotMapped]` properties, not persisted columns.
- `Hospede.Cpf` carries `[CpfValido]` (`Models/CpfValidoAttribute.cs`) — a real modulo-11 check-digit validator, not just a length/format check, and it rejects all-same-digit sequences (`111.111.111-11` etc.) that satisfy the formula mathematically but are never real issued CPFs. It only runs during `ModelState` validation on a controller-bound request, never against rows already in the database, so it doesn't touch existing data — but that's also exactly why `Program.cs`'s seeded guests carry real calculated check digits (`Ana Beatriz Souza`'s CPF ends in `-09`, not the old placeholder `-01`): editing one of them through `HospedeController.Edit` without touching the CPF re-validates it on save, and the old sequential placeholders would fail the real algorithm.

### Guest self-registration vs. reception check-in: same `Hospede`, different required fields

`ClienteController.Registrar` (self-service, `/Cliente/Registrar`) and `HospedeController.Create` (reception/counter, employee-only) both create `Hospede` rows, but only self-registration requires `Login`/`Email` — a counter guest may never get a login at all. Because of that, `Login`/`Email` are **not** `[Required]` on the `Hospede` model itself (that would break `HospedeController.Create`'s `[Bind("Nome,Cpf,Telefone,DataNascimento")]`, which deliberately excludes them and leaves them `null`); `ClienteController.Registrar` enforces both manually via `ModelState.AddModelError`, the same pattern it already used for the Login/CPF uniqueness checks. It also checks `Hospede.Email` uniqueness explicitly before calling `CreateAsync` — `Email` has a database unique index (used by password reset, see below), so without this check a duplicate would only surface as a raw unhandled `DbUpdateException` on save instead of a normal form error.

### Passwords

Both `Funcionario.SenhaHash` and `Hospede.SenhaHash` are hashed with `Microsoft.AspNetCore.Identity.PasswordHasher<T>` — same hasher as before, but now invoked *by* `UserManager<T>` (through `EntityUserStore`, see above) instead of by controllers calling it directly. `FuncionarioController.Create` and `ClienteController.Registrar` both create accounts via `UserManager<T>.CreateAsync(entity, senha)`, which hashes, sets `SecurityStamp`, and persists in one call; `Program.cs`'s seed data is the one exception (inserted directly, so it hashes manually and must set `SecurityStamp` itself — see above). Plaintext password only ever appears as a transient action-method parameter (`senha`)/`novaSenha`, never bound onto the model (`ModelState.Remove(nameof(X.SenhaHash))` before validation) and never persisted or logged. Password rules are configured once in `Program.cs` (`ConfigurarIdentity`, shared by both `AddIdentityCore<T>()` calls): minimum 6 characters, nothing else required — deliberately looser than ASP.NET Core Identity's stricter defaults (which require a non-alphanumeric character among other things and would otherwise reject the seeded `Senha123`).

### Login: unified form, but who picks the username differs by identity

There is one login screen (`Views/Shared/Login.cshtml`, rendered by both `HomeController.Login` and `ClienteController.Login` via MVC's Shared-view fallback — see the `IAutenticacaoService`/`AutenticacaoService` doc comments) — it doesn't ask which kind of account you have. `AutenticacaoService.AutenticarAsync` tries the credentials against `Funcionario` first, then `Hospede`, signs into whichever scheme matched, and the controller redirects accordingly (`Painel` vs. `Cliente/MinhaConta`). The two routes (`/Home/Login`, `/Cliente/Login`) still exist only because `[RequerFuncionario]`/`[RequerHospede]`'s cookie `LoginPath`s and the integration tests hardcode them. `AutenticarAsync` returns `(ResultadoLogin, TipoIdentidadeLogada?)` rather than just the identity type, since a locked-out account (`ResultadoLogin.ContaBloqueada`) needs a different `ModelState` message than plain invalid credentials — both controllers branch on it identically.

Only a guest picks their own `Login` (free-text field on `ClienteController.Registrar`). A `Funcionario.Login` is always system-generated by `FuncionarioController.Create` as `primeironome.sobrenome` (lowercase, accents stripped, numeric suffix on collision) — there's no `Login` input on `Views/Funcionario/Create.cshtml`. The seeded staff accounts follow the same convention: `wesley.sales`/`luan.santos`/`matias.sampaio`/`camila.rocha`/`diego.fernandes`.

### Account lockout and password reset

Lockout is entirely `SignInManager`/`UserManager` behavior via `EntityUserStore`'s `IUserLockoutStore` implementation — no custom counting code. 5 failed attempts within `Program.cs`'s configured window locks the account for 15 minutes (`ConfigurarIdentity`'s `options.Lockout`); a locked-out account is rejected even with the *correct* password until the lockout expires. Password reset (`ContaController`: `EsqueciSenha` → `RedefinirSenha`) asks for the account's **email**, not its login (an employee's login is system-generated and easy to forget — see below) — tries the typed email against `Funcionario.Email` first, then `Hospede.Email`, both of which are unique per table (`AppDbContext.OnModelCreating`, filtered unique indexes so multiple accounts can still have no email at all) so the lookup is never ambiguous. Uses `UserManager<T>.GeneratePasswordResetTokenAsync`/`ResetPasswordAsync` for the actual token work (expiring, single-use via `SecurityStamp` invalidation, all real Identity mechanics). The reset link goes out by real email through `IEmailSender` (`Services/IEmailSender.cs`), implemented by `SmtpEmailSender` (`Services/SmtpEmailSender.cs`, MailKit over Gmail SMTP with an app password — see the README's "E-mail" section for the exact config keys and generating one). The confirmation screen always shows the same generic message regardless of whether that email matched an account — avoids leaking which emails are registered. `CustomWebApplicationFactory` swaps `IEmailSender` for `FakeEmailSender` (`SisHospedar.Tests/FakeEmailSender.cs`) in integration tests, which just captures the email in memory instead of sending it — `IdentityTests.RedefinirSenha_FluxoCompleto_TrocaASenhaDeVerdade` pulls the reset link back out of the captured email body rather than the HTTP response.
